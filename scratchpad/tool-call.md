I want to simplify the tool call execution. 

A tool execution can be multi step. For example: tool executed -> ask for confirmation -> (if confirmed) execute, otherwise not. 
This is a pattern which is being repeatedly displayed by tool calls. I want to find a way to model this using finite state machine. A tool at a given time can only be in a single state. Default state is ideal state, that means, it is not executing. When the LLM invokes this tool, the tool executor starts executing the tool. Then depending on the tool, either it depends on something external like user providing confirmation or providing a file, for it to complete it's execution, so that's a different state like waiting. Then there are tools which simply executes the function and reach completion. A completion state is either successful when we have a tool result, or error then we don't have a tool result or cancelled depending on conditions, we decided not to execute the tool and the final state is cancelled. When the tool is depending on something external then also the completion state can be successful or error or cancelled. 

The major issue comes when we attempt to model this kind of behaviour in LLM, llm by nature are not deterministic so they can follow these deterministic paths. Hence I want to separate out the execution flow from llm and only pass states of tool to llm so based on natural query it can give me a transition state. 

For example: here is one request which I want to model: User asks about weather by saying: "What's the weather?", This query is passed to GEmini and gemini returns the tool "get_weather", THe tool executor starts executing it. It checks for weather location permission is their or not, it realises thhat there is no location permission, it then sends a data to LLM to ask user for permission, if user says yes, then llm informs the tool executor that user has granted permission, then tool continues execution. It gets the weather from weather api and then passes the result to LLM and then LLM says it. 

If you observe the above flow carefully, you will realise that, a tool execution can be dependent on external factors (like user's input). And to complete it, it has to send a partial result to LLM to fetch/ask that information from user. Once that information is available only then does the tool reaches it's completion. 

I want to design a tool executor which handles the above cases, to generalise, when the tools execution depends on outside factors, it reaches a partial stage, then that partial stage is passed to LLM to generate another event, and based on that event the tool completes it's execution.
